# Разбор инцидента безопасности: Утечка данных Capital One (2019)

## 1. Компания и сервис
* **Компания:** Capital One (один из крупнейших банков США).
* **Сервис:** Облачная инфраструктура, размещенная в Amazon Web Services (AWS), в частности — приложение для обработки заявок на кредитные карты и хранилища данных в Amazon S3.

## 2. Уязвимость
Атака представляла собой комбинацию неверной настройки безопасности и подделки запросов на стороне сервера.
* **Тип уязвимости:** SSRF (Server-Side Request Forgery) + Security Misconfiguration (избыточные права IAM).
* **Класс OWASP:**
  * A10:2021 — Server-Side Request Forgery (SSRF)
  * A05:2021 — Security Misconfiguration
* **CWE:** CWE-918 (Server-Side Request Forgery).
* **CVE:** Прямого CVE у инцидента нет, так как это была ошибка конфигурации на стороне Capital One (open-source WAF ModSecurity был настроен некорректно), а не 0-day уязвимость в публичном софте.

## 3. Как обнаружили
Злоумышленница (Пейдж Томпсон, бывший инженер AWS) открыто хвасталась украденными данными в Slack и выложила часть информации (включая скрипты для эксфильтрации и логи) в свой публичный репозиторий на GitHub. 17 июля 2019 года ИБ-исследователь (белый хакер) увидел эту информацию на GitHub и сообщил об утечке Capital One через программу Responsible Disclosure (написал письмо на почту `[email protected]`).

## 4. Ущерб
* **Записи (данные):** Утекли личные данные 106 миллионов клиентов в США и Канаде. Скомпрометировано около 140 000 номеров социального страхования (SSN), 80 000 номеров банковских счетов, а также миллионы имен, адресов, дат рождения и кредитных рейтингов.
* **Деньги:**
  * Штраф от Управления контролера денежного обращения США (OCC) — $80 млн.
  * Выплаты по коллективному иску пострадавшим — $190 млн.
  * Затраты на расследование, уведомление клиентов и юридические услуги — около $100–150 млн.
  * *Итоговый финансовый ущерб:* более $370 млн.
* **Время простоя:** Глобального простоя (downtime) сервисов не было. Атака была направлена исключительно на незаметную эксфильтрацию (копирование) данных, работоспособность банка не нарушалась.
* **Репутация и кадры:** Сильный удар по репутации «самого технологичного банка», увольнение CISO (Chief Information Security Officer).

## 5. Что сделали после (Post-Incident Response)
1. Немедленно исправили конфигурацию WAF, закрыв вектор SSRF.
2. Отозвали и перевыпустили скомпрометированные токены доступа AWS IAM.
3. Тесно сотрудничали с ФБР, что привело к быстрому аресту злоумышленницы (через 12 дней после обнаружения).
4. Ускорили переход на использование более защищенной версии сервиса метаданных AWS (IMDSv2).

## 6. Что должно было быть сделано до (Preventative Measures)
1. **Ограничение SSRF:** Настройка WAF должна была жестко фильтровать исходящие запросы, блокируя любые обращения к внутреннему IP-адресу службы метаданных AWS (`169.254.169.254`).
2. **Принцип наименьших привилегий (Least Privilege):** Роль IAM, назначенная серверу WAF, имела избыточные права. WAF должен был только фильтровать трафик, но его роль позволяла читать содержимое любых бакетов S3 в аккаунте.
3. **Использование IMDSv2:** Вторая версия сервиса метаданных AWS требует обязательного заголовка (токена) при запросе, что делает классические SSRF-атаки невозможными.

## 7. На каком этапе жизненного цикла (SDLC) это можно было поймать
* **Этап проектирования (Design / Architecture):** Нарушение принципа наименьших привилегий должно было быть выявлено при проектировании архитектуры IAM-ролей в AWS. Роль для балансировщика/WAF не должна иметь доступа к бакетам с ПДн.
* **Этап развертывания (Deployment / Configuration):** Ошибка в конфигурации ModSecurity (разрешение на проксирование запросов) могла быть поймана с помощью инструментов Infrastructure as Code (IaC) security scanning (например, Checkov или tfsec).
* **Этап тестирования (Security Testing / DAST):** Автоматизированное сканирование (DAST) или ручной пентест перед релизом инфраструктуры должны были включать проверку на SSRF, особенно попытки достучаться до адреса `169.254.169.254`.
